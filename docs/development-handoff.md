# Aurawolf｜全知之人：保存與開發交接

性質：當前保存／搬站契約。現行版本以 package.json 為準（0.49.6-beta.1）；Site 第 33 版及 0.30.3 ZIP 僅為歷史來源，manifest 已封存於 history/handoff-0.30.3.json。0.49.6 已由使用者授權推送 `main`，沿用既有 Git 整合部署；推送成功仍須另核對線上版號。

## 本階段範圍

- 以手機上的單一上帝操作為主要使用情境。
- 保留現有瀏覽器本機自動儲存。
- 使用者已確認：完整對局存檔匯出／匯入暫不開發，也不是部署或封閉測試的前置條件。
- 現有文字復盤匯出保留；它不是可還原的完整存檔。
- 未來如要新增跨裝置同步、雲端保存或備份／還原，另行確認需求。

## 對局資訊如何保存

| 項目 | 現行實作 |
| --- | --- |
| 保存位置 | 瀏覽器 `localStorage`；不是 HTTP Cache、Cache Storage 或伺服器資料庫 |
| 儲存 key | `moonlit-immersive-prototype-v1` |
| 儲存內容 | 遊戲狀態 `s` 的 JSON，包括板子、座位／角色、規則、日夜階段、技能資源、技能草稿、投票、關係、待結算技能、紀錄及撤回歷史等 |
| 保存時機 | 已確認操作通常透過 `mutate()` → `save()`；部分目標草稿及投票操作會直接呼叫 `save()`，不是所有畫面點擊都會保存 |
| 保存數量 | 同一來源、同一瀏覽器儲存區使用一個 key；保存目前的一局，沒有多局存檔列表 |
| 開新局 | 確認後建立新狀態並寫入同一 key，取代目前對局 |
| 角色狀態版本 | `roleSystem.schemaVersion = 1`；由 `RoleSystem.migrate()` 處理舊資料 |
| 撤回 | 最多 100 個狀態快照；角色結構事件及資訊透過游標還原，細節見 `role-system.md` |
| 失敗提示 | 寫入失敗設為 `saveError`，管理入口顯示存檔失敗；文字紀錄匯出不能恢復技能資源與進度 |

主要實作：`src/app.js`（key、讀寫、初始載入、開新局），
`src/role-runtime.js`（save 包裝、遷移、撤回），
`src/rules/role-state.js`（角色 schema），`src/game-controller.js`（操作及草稿保存）。

0.49.2 增加一般四板的 dayVoting 布林欄位：確認開始放逐投票時保存、下一夜／天亮重設，撤回含此欄位；key／schemaVersion 不變。舊保存沒有此欄位時，已有票單（含棄票）、PK 或第二輪仍視為投票已開始，不能自爆；未記票的一般四板舊白天保存回到討論，由上帝明確開始投票。

0.49.3 一般四板自爆卡的選取者與開啟模式為 controller UI 暫存，不寫存檔；重整回到討論／已保存投票階段，不恢復未確認自爆座號。確認自爆才保存死亡、資源、階段與撤回快照。

## 重新開啟與手機使用限制

- 在相同來源（協定、網域、連接埠）、相同瀏覽器及相同儲存區重新開啟時，會嘗試讀取已保存對局。分頁路徑本身不會隔離 `localStorage`。
- 0.43.0 初始讀取接受無 variant／standard12 的 12 位玩家，或 brothers＋wolfking10 的 10 位玩家；不接受其他縮編組合。舊 12 人存檔補上 standard12，不改 key／角色 schema。這仍不是完整的存檔結構驗證。準備階段重新載入時，角色會重設為未確認，撤回歷史會清空。
- 讀取／解析異常目前會被捕捉，初始狀態不採用該資料；後續角色系統遷移仍有自己的版本檢查。不要將這套流程描述為保證能恢復任意毀損存檔。
- 已保存的遊戲進度與畫面暫存不同。尚未確認的認牌座位選取、尚未送出的主持筆記、彈窗／抽屜狀態，以及發言計時器等在記憶體中；重整或手機終止頁面後不保證恢復。
- 換裝置、換瀏覽器或從通訊軟體內建瀏覽器改用 Safari／Chrome，不應假設共用同一份資料。
- 無痕模式、清除網站資料、瀏覽器／作業系統回收儲存空間，都可能造成進度無法保留。單純清除圖片／HTTP 快取與刪除網站儲存資料不同。
- 沒有跨分頁同步或衝突處理；同一來源開多個分頁操作可能互相覆蓋，測試時應以單一分頁主持。
- 沒有完整離線支援；頁面已開啟不等於斷網後能重新載入網站與所有圖片。

## 部署／搬站的影響

- 從 Sites 網址搬到自有網域、Vercel 網址，或切換不同預覽網址時，來源不同，原有對局不會自動搬移；舊網址的儲存資料也不會因此自動被刪除。
- 本階段接受在新網址開新局，不為搬遷新增存檔匯入／匯出。正在進行的對局宜在原網址完成。
- 同一來源更新網站不會由 Hosting 自動清除 `localStorage`，但後續程式的遷移及初始化仍可能改動資料；發布前應驗證舊進度相容性。
- 測試站宜保留固定網址；新預覽網址看不到舊進度，不等於自動儲存失敗。
- 不可隨意更換儲存 key、清除 localStorage 或改動 schema 來解決 UI 問題。若確有需要，先設計相容性／遷移方式。

## 圖片快取與對局存檔分開

角色圖是 `src/assets/roles/` 的 WebP，建置後在 `dist/assets/roles/`。
HTTP 快取由瀏覽器與 Hosting 回應控制；`portraitPreload`、`portraitNodes` 是目前頁面的記憶體預載／解碼及圖片元件快取，重新載入頁面後會重建。
這些快取不保存角色分配或遊戲進度。未使用 Service Worker、IndexedDB 或 Cache Storage 保存對局。

## 本機開發／MCP 接手原則

- 交接完整 `src/`、角色素材、`build.cjs`、測試、`AGENTS.md` 與 `docs/`，不能只交付 `dist/`。
- 先閱讀 `AGENTS.md` 與 `docs/role-system.md`；UI 修改維持在呈現層，遵守 GameEngine／controller 邊界。
- 現有建置指令是 `node build.cjs`，發布內容為 `dist/`；不需 Sites 執行期 API 或後端服務。
- 對局資訊包含未公開角色與技能目標；排查時避免把實際玩家完整 localStorage 內容無意間貼入公開 issue 或共享日誌。
- README、統一 dev／preview／build／test 指令、版本標示、八板規則與已知限制已補齊。使用者已完成前版本機驗證；本機 MCP 連接、自有 Hosting 與最新手機回歸尚待使用者環境執行。

## 0.30.4 角色圖片備援

`portrait()` 保留帶有內嵌 SVG 角色剪影的容器，正式圖片放在容器內，解碼成功才顯示。
預載或顯示節點失敗時保留剪影，不改角色名稱、規則或存檔；後續掛載可重試。
開局圖片準備總等待上限為 8 秒，即使失敗／未完成仍允許開局；背景佇列繼續處理。
預載與顯示解碼各自也有 8 秒上限，以釋放等待中的應用層佇列；不強制取消瀏覽器下載。
切板／關閉詳情仍會取消原本開局意圖；遲到的完成通知不再次開局。
目前 24 張新版圖原位元組與成功快取重用保持，Safari／Chrome 的實際視覺與網路行為仍待驗證。
